## 4. Prueba física

El operador presentó el llavero con el firmware productivo `CERRADURA` y la
puerta abrió. La decisión quedó auditada:

| Tabla | Fila | Datos |
|---|---|---|
| `key_access_events` | 756 | `key_id=468`, `credential_type=NFC`, `result=OK`, `room_id=14`, `device_id=d443229fc114`, `2026-11-03 12:30:44.315` |
| `access_events` | 8094 | `QR_VALIDATE`, `OK`, sala 14, `12:30:44.317` |
| `access_events` | 8095 | `OPEN`, `OK`, sala 14, `12:30:44.320` |
| `worker_sessions` | 573 | trabajador 172, sala 14, `entered_at=12:30:44.312` |

El firmware abre el relé tras recibir HTTP 200 de `/api/v1/qr/validate`. El
backend usa `LOCK_PROVIDER=LOCAL`, por lo que no envía ningún comando de red.

> Nota de auditoría: `AccessKeyService::normaliseProvider()` mapea `LOCAL` a
> `SIMULATED`, por eso la fila 756 muestra `provider=SIMULATED`. El gateway
> real es `LOCAL`; el desplazamiento físico lo hace el ESP.

## 5. Flujo verificado

1. El R35D-B lee el llavero y envía `00EFA5BB` por UART1.
2. El firmware lo envía como `qr_text` a `/api/v1/qr/validate`.
3. El backend lo clasifica como ficha (sin token, sin `.`), normaliza el UID y
   lo busca por hash.
4. Comprueba ficha `ASSIGNED`, llave `NFC` activa, trabajador activo, vigencia,
   sala resuelta desde el lector y permiso por tipo de sala.
5. Responde `allow`; el ESP abre el relé; se audita `NFC OK`, `QR_VALIDATE` y
   `OPEN`.

| `IMAN 2.6-ota` | `bd886ab3c35475dccadffc2fcc02457f8e1c2d56ed9d83fa6f3403395b5c5acd` |

Tras el diagnóstico se restauró `CERRADURA 2.6-ota`; el dispositivo 23 lo
declara en su heartbeat. Si se repite una prueba que flashee otro sketch, hay
que volver a cargar `firmware/esp-cerradura/` con
`firmware/flash-variant.sh --variant=CERRADURA`.

## 7. Limitación de seguridad

Un llavero EM4100 es de solo lectura y su UID es clonable; usar el UID como
credencial no protege frente a una copia. Para mayor garantía, usar un T5577
con un código secreto y mantener el mismo flujo `ficha_code`.
